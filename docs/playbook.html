Bootstrap-environment · any stack · any agent tool · v0.1.0

Set up any project, then run it with one Chief of Staff and a named session family

This page is the human-readable version of the bootstrap-environment skill. Part one sets up the project: it detects the stack, installs dependencies from the lockfile, finds the best free plugins in the marketplaces and on GitHub, and proves each one works. Part two covers how the work is run afterwards: who does what, how a task moves, and which files hold everything.

The idea in six lines

  1. Detect, don't ask. The stack, the lockfiles, the gate command and the work already in flight are read from disk. The owner is asked only the boundary questions and the session names.
  2. Install automatically, within hard stops. Dependencies, plugins, language-server binaries and each session's kit are installed without a stop gate. Anything paid, elevated, account-creating or unread is never installed.
  3. The owner talks to one session, the Chief of Staff. The family is staffed like an IT company: nine core sessions with fixed role IDs, Platform and Support started on demand, and any project lanes the owner names.
  4. Each session knows its job and carries only its kit: the skills and plugins its role needs, and nothing that belongs to another role.
  5. Everything lives in the repository: one board, one pending register, one log per session, one file per lesson.
  6. The owner's word moves code to live. It is typed in the releasing session's chat or relayed by the Chief of Staff with the exact words, the question that was asked, the shas, the pasted check and the sign-offs. Hotfix is the one shortcut, for live breakage only.

Part one: the bootstrap, phase by phase

0
Probe (read only)
Runtimes, checked by running --version. A stack profile built from manifests and lockfiles. Brownfield state. Every agent's history on disk. Deploy blast radius. Secrets (where they are, never their values). Then the boundary questions to the owner.
1
Baseline
The context cost of always-loaded files and tooling, in characters and tokens. The final report is judged against this number.
2
Dependencies by stack
Lockfile-exact installs for each workspace, after the runtime version is checked. Then one scripts/bootstrap that runs the same way locally, in every worktree and in the cloud hook.
3
Plugin discovery
For each need (language server, framework, browser, design, security, docs, services), search what is installed, the added marketplaces, the official marketplace and GitHub. Score the candidates, run the trust check, and pick one per need.
4
Install
Settings are backed up first. Plugins go in at project scope with their server binaries. GitHub sources are pinned to a commit SHA.
5
Verify
A real LSP query, a real MCP call, a real browser action, and every branch of every hook. Only what passes is enabled; the rest is marked BLOCKED with the action that would unblock it.
6
Scaffold
AGENTS.md, the board, the register, memory, the gate and the memory CLI. Existing conventions are absorbed, never overwritten.
7
Session family
The owner names the sessions, each kit is narrowed per worktree, then the sessions start in order and each one restates the rules.
8–10
Seed, prove, report
Mine lessons from history, deliberately break check to show it catches the fault, run the gate and one real user path, then report PASS, PARTIAL, BLOCKED or FAILED. No feature work starts until the owner says so.
Hard stops, even in automatic mode: anything that costs money, needs an account or asks you to accept terms. Anything that needs admin rights or a system-wide install. Anything that touches a REAL database or service. A GitHub plugin whose hooks and MCP config have not been read. More than two existing files changed at once. HIGH or CRITICAL work without the owner's typed go.

Plugins: search everywhere, pick one per need

Where it looks

  1. Plugins already installed on this machine
  2. Marketplaces already added
  3. The official Anthropic marketplace
  4. GitHub: gh search repos, gh search code for .claude-plugin/plugin.json, the framework's own org, and a web search

How it chooses

  • Must: fits this stack and version, has a usable licence, is free, and doesn't duplicate another pick
  • High: official (Anthropic or the framework's org), maintained (commits in the last 6 months)
  • Medium: adoption (stars, forks), context cost
  • Trust check (non-official only): reject on hooks that call the network or run downloaded code, on obfuscated code, or on unpinned npx/uvx MCP servers

Part two: the session family

Nine core roles start in every project. Platform and Support (dashed cards) start when there is a live system or real users; until then Release Ops and the Librarian cover their duties. Role IDs are fixed. They name the log files and are the words used in AGENTS.md. Display names come from the owner. Before starting anything, the Chief of Staff shows one table (role, its job in this project, a proposed name, its kit), and the owner confirms or renames each one and chooses which project lanes to add. Model routing: the strongest model for the Chief of Staff, a mid model for the rest, the cheapest for the Librarian. Hotfix always runs in the cloud. Remote Control is on for every local session.

Chief of Staff chief-of-staff · strongest

JobThe owner's single contact. Turns asks into tasks, decides risk, assigns work, re-reads every commit from the remote, relays the owner's words, keeps the sign-off grid, nudges idle sessions, verifies live and closes rows.
KitSession tools, the artifact reader, read-only git, a cheap gatekeeper agent, a scout agent for reads, memory notes.
NeverPushes live, runs server commands, decides for the owner, delegates a decision, relays more than the owner's question covered.

Librarian librarian · cheapest

JobLessons, the decisions trail, board and register hygiene, the research and artifact index. Sends "lessons that apply" at each task start and asks "log + lesson?" at each hand-off.
KitMemory CLI (mem, check, index, report), a memory-consolidation skill. Docs commits only.
NeverCode, decisions, blocking anyone, editing AGENTS.md on a relayed word.

Researcher researcher · mid

JobFacts before design or build: code with file:line, real volumes read-only, what other systems do, options with trade-offs.
KitCode search and scout agents, the stack's query and timing tools, EXPLAIN on a copy, library-docs lookup, a browser, read-only Playwright timing.

Design design · mid/strong

KitThe Artifact tool with artifact-design, DESIGN.md, frontend-design and design-review skills, a UI/UX reference skill, dataviz.

Builder builder · mid

KitPlaywright and a browser, crawl and timing scripts, figure checks, its own database copy, a test-strategy skill.

Tech Lead tech-lead · strong

JobThe senior engineer. Writes architecture decisions as ADRs, owns code standards, and reviews every code diff for correctness and design. Owns schema and migration review and the independent review of HIGH work. Plans dependency upgrades as their own rows.
KitThe framework plugin and LSP, code-review and PR-review skills, an architecture skill, the stack's migration and schema diff tools.

Security security · mid/strong

KitThe security-review skill or the claude-security / security-guidance plugins, the stack's dependency audit, a secret scanner, an OWASP-style checklist.
NeverFixes code (it files findings to the Builder), signs off its own fixes, scans live.

JobReleases batches the sign-off grid shows complete. Pre-stages a dry run (merge, gate, migration list) before asking. Pushes live on "release <scope>", typed in its chat or relayed by the Chief of Staff, with the pre-release check pasted. Watches the deploy and merges back.
KitRelease worktrees, the gate, the version endpoint, a deploy-checklist skill.
NeverHotfixes, HIGH builds, a release without the pasted check, a peer's message taken as the release word.

Hotfix hotfix · mid · cloud

JobLive breakage only: reproduce, fix, gate, short QA check, then push live on "apply", typed in its chat or relayed by the Chief of Staff. Owns the server lines the owner runs, each reported first. When it moves to the cloud, its local copy is archived at once.
KitThe cloud start hook (bootstrap plus a throwaway database), systematic debugging, cherry-pick onto live.
NeverFeatures, redesigns, any push without "apply", running locally.

Platform platform · on demand

JobThe running system: CI, environments, the shared database server and per-session copies, backups and restore drills, monitoring, error logs, performance budgets, a post-deploy watch and infrastructure cost. Writes every server line for the owner. Started once there is a live environment.
KitCI and container tools, the database client, read-only monitoring and logs, an SRE runbook skill, the deploy checklist.
NeverPushes live, runs server commands itself, changes infrastructure without a HIGH go.

Support support · on demand

JobThe users' voice. Turns user reports and error spikes into board rows with steps to reproduce, triages severity (live breakage goes to Hotfix), and writes user-facing release notes and help pages. Started once real users exist.
KitA ticket or feedback connector if the project has one, a UX-copy skill, the browser on the invented-data copy.
NeverCode, promising users dates, sharing real user data.

Project lane optional · 0..n · owner names it

JobOne cross-cutting area, such as onboarding, billing, integrations or a mobile app. Same rules as Builder, with its own branch and its own rows.
KitThe Builder's kit, plus throwaway databases for fresh-install proofs and writing-plans before any HIGH step.
NeverLive, HIGH work without the go, another lane's files without coordinating.

How a kit is enforced: plugins are installed once at project scope. Each session's worktree then turns off everything outside its kit in its own .claude/settings.local.json. Every session's skill list is checked to confirm it shows only its kit. A stack skill that doesn't exist for this stack is left out, never replaced with one for another stack.

The owner's word, typed or relayed

Three words move things: a HIGH go, "release <scope>" and "apply". Each one counts when the owner types it in the acting session's chat, or when the Chief of Staff relays it. All risk levels qualify. A relay must carry all four of these:

1 · Words and question

The owner's exact words and the date, plus the question exactly as it was asked. The answer covers only what the question covered.

2 · Scope

The shas, in the order they sit on the dev branch. For a go, the board row and what it covers.

3 · Pasted check

The output of the named pre-release check. No pasted check means no release.

4 · Sign-offs

The piece's row in the sign-off grid, with every box filled.

The relay is written on the board before it is sent. The acting session echoes the scope back and refuses on any mismatch, any paraphrase without a scope, or any brief that names more than the owner's question did. Only the Chief of Staff relays, and a peer's message is never the owner's word. Why relays are allowed: relays were first forbidden, and signed-off work then waited for hours. The real risk turned out to be scope, not which chat the word was typed in: a brief once covered more than the owner's "yes", and two commits had to be reverted.

Keeping many sessions in step

  • Sign-off grid on the board: piece · sha · QA · Design · Tech Lead · Security · Librarian · Chief of Staff · date. No session approves its own work. An empty box blocks the push. Docs-only and picture-only commits skip the Librarian box.
  • Freeze only when every sign-off is in. A fix after a freeze re-opens QA, Design and Release Ops for that piece. In one release, "frozen" was followed by "one more fix" four times.
  • Every message names its sha and says "supersedes X" when it replaces an earlier one. Queued messages arrive late: a Builder acted on a withdrawn ruling, and QA tested a stale tip.
  • Mind the message cap (roughly 10–20 between owner turns). Send fewer, fuller messages. When a chain stalls, ask the owner to type anything.
  • Nudge idle sessions. A session waiting on a background job can stop.
  • Render what workers can't open, such as PDFs, into images before handing them to QA and Design.

How the rules are enforced

Rules that live only in prose get skipped, so four layers check them:

LayerWhat it catchesWorks in
1 · Pre-tool guard (guard.mjs)Force-pushes, --no-verify, hook tampering, server commands, live pushes by the wrong role, docs-only roles writing code, protected configClaude Code, and other tools where a hook can block
2 · Per-worktree permissions (bootstrap role)The role's deny list; plugins narrowed to its kitClaude Code; partly elsewhere
3 · Git pre-push (.githooks/pre-push)Code without complete sign-off files for that sha; live pushes without a release record; deleting live or dev; conflict markersEvery tool and every human
4 · Server branch protectionAnything pushed from a machine without the hooks, including cloud agentsThe git host (turn it on)

Sign-offs are files, one per role per piece: bootstrap signoff <piece> --verdict PASS writes docs/signoffs/<piece>/<role>.md with the sha. A release record comes from bootstrap release, which refuses to write one without the owner's words, the question, the shas and a pasted check.

Starting the family

  1. Run the bootstrap (Phases 0–6). The owner answers the boundary questions.
  2. The Chief of Staff shows the naming table. The owner confirms names, kits and project lanes, and the mapping goes into AGENTS.md.
  3. Each writing session gets its own worktree, where scripts/bootstrap builds real dependency folders (never links to another checkout) and its own database copy. Its kit goes into settings.local.json. There is one local database server, started once outside any session; check the port before starting another.
  4. Start order: Librarian, Release Ops, Hotfix (cloud), Tech Lead, Security, QA, Researcher, Design, Builder, then Platform and Support when due, then the project lanes. Remote Control is on for each one.
  5. Each session's first message carries its role row, its kit, the full rules (not a summary) and its hand-over. It restates the rules, lists what it inherited and names its first action, then waits for confirmation.
  6. Start ritual, every time: AGENTS.md, the board, the lessons its rows name, then print its rows. End of every task: the row is updated, the log is pushed, and a lesson is written (or "no lesson" is recorded).
  7. The owner archives old sessions only after the new family has acknowledged.

Mistakes already paid for

  • Sessions acknowledged a summary of the rules, not the rules themselves. Brief with the whole section and audit against it.
  • Two sessions linked their dependency folder to another checkout and tested the wrong code.
  • On Windows, python resolved to a Store stub. A path check passed while the runtime was missing.
  • A guard hook crashed on load and silently allowed everything. Hooks are run before they are enabled.
  • A capability boundary between agents was assumed and turned out false. Probe it, don't assume it.
  • The local setup and the cloud setup were described separately and drifted apart. One scripts/bootstrap serves both.
  • A database server ran inside one session's preview process and stopped five times in a day.
  • Work went to a stale local Hotfix for two days after Hotfix had moved to the cloud. Archive the local copy at once.
  • A relay brief covered more than the owner's "yes", and two commits were reverted. Quote the owner's question, and scope only to it.
  • A screen piece nobody asked about had no shots, so Design nearly missed it. Two approved artifacts also contradicted each other.
